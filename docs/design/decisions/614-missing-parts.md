# #614 #603 で表せなかった部品: 入れ子の繰り返し・線の束・cylinder の高さとはみ出しの寸法・シーケンス図・セットのラベルと点線

## 背景

#603 の dogfooding（v0.19.1 の Skill で 10 本の資料から図を作る）で、次の 5 つが Sumi で表せないか、表しにくかった。

1. 入れ子の繰り返し（run 3: ×4 の中に N× のブロック）。`×4` は attach したラベルで書けたが、N× は文で補った。
2. 並行する線の束（run 6: mHC の 4 本の残差の流れ）。1 本の線で代用し、主題の 1 つが見えなくなった。
3. cylinder の高さ（run 3・7・8）と、`label-overflow` のヒント（run 10 のひし形）。cylinder は 2 行のラベルに 23mm 必要で、明示した高さが足りないとヒントの数値を手で試し、ひし形のヒントは収まる寸法を示さなかった。
4. シーケンス図（run 9）。隠しジャンクション 18 個と線分 18 本で組み、y 座標を手で並べた。
5. セットの帯のラベルの大きさ・太さ、凡例の点線の見本、点線かつ muted の線（run 9）。

Sumi の原則（汎用の部品、分野固有の必須部品を作らない、既存の出力を変えない）に沿って、それぞれ要否と形を決めた。

## 決定

### 1. 入れ子の繰り返し: 新しいフィールドは足さず、既存の部品の組み方を Skill に書く

- 内側の繰り返しは `dashed` のグループと attach した `×4`、外側は グループに attach した `bracket` と、その bracket に attach した `N×`（`text: large`）で書ける。attach はグループにも効き、内側のラベルは外側の枠の中に入る（外側の枠がそれを含むよう広がる）。描いて確かめた（`structured.md` の nested repeats の例は `expect-render: fits` でテストされる）。
- `groups[].repeat: "N×"` のような糖衣も検討したが、中身は attach したラベルと同じで、幅の費用（run 3 の 10mm）も変わらない。枠の内側の角に入れる案は、パディング（3〜4mm）に大きめの文字が入らず中身と重なる。新しい書き方を覚えさせるより、既存の部品の組み合わせを Skill の表（layout-tips）と structured.md の例で示す方が安い。
- 採らなかった案: 外側に括弧を自動で描く `repeat` フィールド（bracket の attach と同じ結果で、二重の書き方になる）。

### 2. 並行する線の束: `edges[].strands: 2–5`（structured のみ）

- 辺を、その経路に沿った n 本の平行線として描く。線の中心どうしの間隔は線幅の 2 倍（線の間に線幅 1 本分の隙間。どの線幅でも同じ見え方）。経路は今までどおり 1 本としてルーターが引き、描くときに左右へずらす（`src/render/bundle.ts`）。
  - 曲がり角は、元の経路の角の丸めと同じ中心の同心円で丸める（内側の線は半径 − ずれ、外側は ＋ ずれ、内側で 0 以下なら尖らせる）。半径は各脚の半分まで（ワイヤーの丸めと同じ上限）。直角でない角は尖ったまま（直交の経路と `route: straight` しか来ない）。
  - 矢じりは 1 つ。線は矢じりの底で止まり、矢じりは束を覆う大きさに自動で拡大する（`bundleArrowheadScale()`: 幅 ≥ 2·n 本分の線幅、0.25 刻み、1〜2）。辺が `arrowheadScale` を書いたときはそれを使う（ルーターの余白と lint は `style.arrowheadScale` を読むので、拡大はどこでも一貫する）。
- 束は他の辺と幹（trunk）を共有しない（ネットの線の合成から外し、独立に描く）。`path.connection`（検査・lint の経路・編集可能 PPTX）は経路そのもの 1 本のまま。編集可能 PPTX は束を 1 本のコネクタで描くので、黙って失わないよう `pptx/bundle-as-one-line`（warning）を出す（各線を個別の図形にすると、コネクタの接続と矢じりの扱いが SVG と一致しなくなるため、最初は報告にとどめた）。`themeOverrides.edgeCorners: sharp` では全部の線を尖った角（ずらした角の点）で描く。lint が測る描いた線（`paintedEdges()`）は全部の線の片と円弧を持つので、束に重なる線は `edge-near-edge` が報告する。
- 曲線（`route: curve`）と `zoom` の辺には付けられない（`component/invalid-prop`）。auto エンジンでは `layout/structured-only`。凡例の `edge` の見本も `strands` を取る。
- 採らなかった案:
  - **太い線を地の色で抜く**（太線の上に細い地色の線を重ねて n 本に見せる）: 角の処理は SVG 任せで済むが、透明な背景・塗りのあるパネルの上で抜いた部分が地の色にならない。
  - **「/4」の斜線の印**（回路図のバス幅の表記）: 本数は伝わるが、#603 の依頼（4 本の流れが B_l で混ざるのを見せる）には平行線そのものが要る。必要になれば辺のラベルで書ける。
  - **ルーターが束の幅を避ける**: 経路の探索に辺ごとの太さを持ち込むと全図の配線が変わりうる。最初は描画だけにし、近すぎる線は lint に任せる（Skill に「束には専用のアンカーを」と書いた）。

### 3. cylinder の高さと、はみ出しの寸法

- **`cylinder` の `props.capDepth`（structured のみ）**: 楕円の蓋の深さを書ける。ラベルに合わせた cylinder の高さは「ラベル＋パディング＋蓋の深さ × 3」（上の蓋の楕円全体と下の蓋の前半分）になり、`2pt` なら隣の箱とほぼ同じ高さになる。`props.height` を書いたときは蓋が高さの 1/3 を超えない。
  - 既定（省略）は今までの `cylinderArc()`（D2 の 24 unit、低い cylinder では浅く、高い cylinder では深く、#516・#547）のまま。既定の蓋を幅から決め直す案（レビューの提案）は、examples・ギャラリーの cylinder をすべて変えるので採らなかった。
  - 高さが文字に合わせて伸びることは、高さを書かなければ今もそうなっている（幅だけを書いても高さは伸びる）。#603 の不満は、蓋が 12pt ずつ取るので 2 行のラベルで 23mm になることと、明示した高さが足りないときの寸法探しだった。前者を `capDepth`、後者を次のヒントで解く。
- **`geometry/label-overflow` のヒントに収まる寸法を足す**（`src/lint/geometry/label-fit.ts`）: `props.width` / `props.height` を書いたノード（structured、組み込みの形。outline 部品・アイコン・キャプションを除く）で、ラベルが形の文字の領域に収まらないとき、
  - 描いたラベルの行を形のラベルの中心に保ったまま、0.5mm 刻みで (a) 高さだけ、(b) 幅だけ、(c) 両方を同じ比で大きくし、収まる最小の寸法を探す（面積が最小のもの。同じなら高さだけ → 幅だけ → 両方。幅はページで制限されることが多いため）。円・正方形は辺 1 つ。判定は lint と同じ `labelArea()` と `rectDepthInside()`（cylinder は蓋、`capDepth` を含む）。
  - その寸法を IR の写しに書き、描画と同じ手順（`placeStructured` → `routeStructured` → SVG → この規則を含む全 geometry 規則）で試す（`trial.ts`、#621 の `relocatable`・#613 の `content-band` と同じ）。配置に error がなく、そのラベルの `label-overflow` が消え（設定した重さによらず、規則の判定そのもので確かめる。info や off にしていても見逃さない）、元の図の写しと比べて新しい error / warning がないときだけ「Verified: props.width: 25mm, props.height: 15mm fits the label …」と書く。新しい問題（ページ幅の超過など）が出たら寸法とその問題のコードを書き、試せなかったときは理由を書く。
  - 費用: 明示した寸法のノードがはみ出したときだけ。1 図につき最大 4 ノード（`MAX_FIT_TRIALS`）と元の図 1 回。`HintTrials` の大きさの上限を超える図、HTML・外部ファイルの画像を含む図、ほかの規則の試しの中では試さない（`inHintTrial`）。
  - 今までのヒントの文（cylinder の「props.height of at least …pt」など）は残し、その後ろに足す。auto エンジンの図（D2 がラベルを置く）には足さない。
  - ひし形の寸法を式で出す案（ラベルの箱の角が辺の内側に入る条件）も考えたが、形ごとの式を持つより、lint と同じ判定で探して試す方が、cylinder・楕円・六角形・平行四辺形にも同じ仕組みで効く。

### 4. シーケンス図: この PR では実装せず、#630 に分けた

- lifeline・順序のあるメッセージ・注記・帯（fragment）を y 座標なしで書くには、arrange の新しい箱（`chat` と同じ位置づけの `sequence`）、列の間隔をメッセージのラベル幅から決める配置、行の順の配線、lint の確認が要る。#614 の他の項目と同じ PR に半端に入れると、書き方を後から変えにくい。設計案と受け入れ条件を #630（v0.20.0）に書いた。
- それまでの代わりの書き方（`place` と隠しジャンクション、`variant: muted, dash: dashed` の lifeline、`rect` のセットの帯に太字の見出し）を Skill の layout-tips の表に書いた。この PR の 5 の部品（`dash`、セットのラベル）はその代わりの書き方と #630 の両方で使える。

### 5. セットの帯のラベル、凡例の点線、点線かつ muted の線

- **`edges[].dash: dashed | dotted`**: variant とは別に、線を破線（その部品の `dashed` の破線）か丸い点にする。色・線幅は variant のまま（`variant: muted, dash: dotted` で淡い点線）。テーマの解決（`withDash()`）で効くので両エンジンで使え（auto の点線は D2 の最も細かい破線）、`dim` も今までどおりかかる。
  - 合成した variant（`muted-dotted` など）を足す案は、emphasis・tone・muted と破線・点線の組み合わせの数だけ variant が増え、テーマごとに層を足す必要がある。`dash` は 1 つのフィールドで全部の組み合わせを書ける。
- **凡例の点線の見本**: `edge: {variant: dotted}` の見本は 0.16.0 から描けていたが、structured.md の凡例の節に「there is no dotted line」と古い記述が残っていて、run 9 はそれを読んで諦めていた。記述を直し、見本の `edge` に `dash`（と `strands`）を足した。
- **`sets[].text` / `sets[].weight`**: セットのラベルの大きさを `small` / `body` / `heading`（既定。グループの見出しの大きさ）/ `large`（箱の文字の 1.5 倍）で、太さを `bold` / `regular` で選べる。ノードの `text` / `weight` と同じ語にした（自由な pt は書かせない）。省略時は今までどおり。

## 互換性

- 追加したフィールドはすべて任意で、省略時の出力（examples・ギャラリー・ゴールデン・再現図のハッシュ）はバイト単位で変わらない（`gallery:check` と全テストで確認）。
- lint の出力: 明示した寸法のノードの `geometry/label-overflow`（structured）のヒントに、収まる寸法の文が 1 つ増える。今の examples・fixture にこの診断はない。
- JSON Schema（`schema/figure.v1.schema.json`）を再生成した。

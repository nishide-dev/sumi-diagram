# #577 傾けた平面 `plane` と平面をまたぐ対応線（設計 #574 の段階 C）

- **背景**: 同じノード集合を持つ 2 つのグラフ（多層ネットワーク、時系列のスナップショット、グラフマッチング）を、傾けた平面に上下に重ねて対応を線で見せたい。見た目の決定は `research/574-3d-components/`（planes のモックアップ）にあり、斜投影（cabinet）の 2D 外接形に落とす方針は #574 と #575 のとおり。この記録は段階 C の実装上の決定。
- **決定**:
  - **スキーマ**: 新しい部品は作らず、`container` グループの `props.plane: floor | wall`（省略可）にした。部品を足すとテーマごとのスタイル表（`sumi/container` の variant・tone・枠・`dim`）を全テーマに複製することになる。平面は「枠が平行四辺形になるコンテナ」なので、`variant`・`tone`・`lineWidth`・`dim` はそのまま効く。投影は `figure.projection`（段階 A）と同じ値（既定 45°・0.5）を IR の `GroupIR.plane: {orientation, angle, depthScale}` に確定する。`plane` を書かない図の IR・レイアウト・出力は変わらない。
  - **座標変換**: 中身は平らな枠（flat frame, W × H, y 下向き）に通常の arrange（`place`・`row`・`stack`・`grid`・`attach`）で置く。平面座標は `u` = 枠の左辺からの距離、`v` = 下辺から上向きの距離。`k = depthScale·cos(angle)`、`m = depthScale·sin(angle)`（ページの y は下向き）として、
    - `floor`: `x = x0 + u + v·k`、`y = y0 − v·m`（研究どおり）。外接形は `(W + H·k) × (H·m)`。
    - `wall`（奥へ退く縦の平面。cuboid の側面と同じ向き）: `x = x0 + u·k`、`y = y0 − u·m − v`。平らな枠の x 軸が奥行き、y 軸が上。外接形は `(W·k) × (W·m + H)`。
    - `(x0, y0)` は平行四辺形の外接形の左下で、どちらの向きでも (u, v) = (0, 0) の行き先。実装は `src/layout/plane.ts`（純粋な関数: 基底・外接形・正逆写像・四隅・線分の凸多角形への切り取り）。
  - **レイアウトの組み込み**（`structured/engine.ts`）: 平面グループの測定寸法は平らな枠の外接形に、手前の辺の下のタイトル帯（行の高さ + `captionGap`）を足したものにする。親の stack・row・grid は平面を投影後の高さで詰める。配置では、外接形の左下と平らな枠の左下を一致させ（タイトル帯はその下）、子を平らな枠で通常どおり置いてから、各ノードの中心だけを写す。ノードの大きさ・形は変えない（円は円）。中の文字・バッジ・グリフは写したノード矩形に従うので水平のまま。写す前の矩形は `LayoutIR.planes[].flat` に残す（配線用）。`GroupLayout.rect` は平行四辺形の外接形、`GroupLayout.quad` は四隅（手前左・手前右・奥右・奥左）。タイトルは手前の辺の下に左寄せ（外接形の左端）、`labelAt` は無視する。平面は自然な大きさのまま、割り当てられた領域の左・下に寄せる（`stretch` で広げない）。
  - **配線**（`route/planes.ts`）: 同じ平面の 2 ノードを結ぶ普通の辺（`route` なし）は、その平面の平らな枠だけの小さなレイアウトとして従来のルーターで配線し、折れ線を同じ変換で写す。直交の脚は平行四辺形の辺に沿う。写した端点は直立ノードの外形に取り付ける（平らなノードの輪郭は写すと円の内側になるので、最初と最後の脚を円の輪郭まで延ばす）。辺のラベルは写した中心に平行移動する。ネットは平面ごとに番号を足して結合する。`route: straight` は写した 2 ノードの間の直線で、ルーターの直接配線（`diagonal.ts`）がそのまま円の輪郭で止める（平面座標で配線して写しても同じ直線になる）。`route: curve` は写さずページ上で描く。平面をまたぐ辺・平面と外の辺はページ上で配線する（`route: straight` を推奨。対応線）。
  - **対応線の描き分け**（`render/structured.ts`）: 平面をまたぐ `route: straight` の辺は、2 つの平面のうち上にある側（ページの下端が高い方）が隠す。描画順は、平面でないグループ、平面を下のものから順に（枠）、の間に、対応線を「下の平面の後・上の平面の前」で挟む。上の平面の fill が線を隠し、その後に平面内の部分だけを薄く（線の色をキャンバス側へ 60% 混ぜて）描き直す（`sumi-plane-ghost`。図の要素ではないので inspection・lint には現れない）。研究の案 V3 のとおり。薄い部分は線と同じ dash・太さ・キャップで、平行四辺形との切り取りは Cyrus–Beck。`wires()` は直線の線の描画を呼び出し側が差し込めるよう `deferred` を返す。
  - **lint**: geometry lint は SVG の inspection を測るので、変換後の形が自然に対象になる（平行四辺形の枠は `<polygon>` で、その外接形が group の bbox、写したノードと辺）。平面の外接形は 2 つの空の三角形を含むので、`geometry/group-empty-area` は平面を測らない。タイトルは枠の外にあるので `geometry/label-overflow` は平面のタイトルを免除する（`above-*` の免除と同じ扱い）。平らな枠では離れているノードが写すと重なることがあり（`geometry/node-overlap`）、壁で対応線が上のノードを貫くと `geometry/edge-through-node` が出る。どちらもテストで確認した。
  - **PDF / PPTX**: PDF は SVG 経由なので平行四辺形とそのまま写る。編集可能 PPTX は SVG を読むので、平行四辺形は自由形状（`custGeom`、4 点の閉じた経路）、平面内の辺は写した点の自由形状になる。z 順は SVG の group の順（下の平面から）に従う。**制限**: PPTX の辺は従来どおり全ノードの後に描くので、対応線は平面の上に出て、薄い部分（ゴースト）はない。PPTX では隠しを実装しない（SVG は図の要素の複製を避けるために別の要素で描いたが、PPTX の部品は要素から作る）。
  - **catalog・スキーマ**: `container` の props に `plane` を足した（catalog・ギャラリーの container の表に出る）。JSON Schema は変わらない（`schema:check` が一致）。check ステージで、`plane` は structured のみ（`layout/structured-only`）、`layers` と併用不可・`plain` 不可（`component/invalid-prop`）、平面の中にグループを置くと `layout/plane-nested-group`（置いた場所を指す）。
  - **Skill**: `structured.md` に「Tilted planes」の節（変換の式・配線・対応線・lint と出力・できないこと）、`figure-format.md` の機能表（0.19.0）、`SKILL.md` の構造化の部品の一覧、`diagnostics.md`、ベースレイアウト `stacked-planes`（sumi テーマ、床の平面 2 枚、同じ 6 ノード、点線の対応線、凡例）。
- **採らなかった案**:
  - 新しい部品 `plane`（グループ部品）: テーマのスタイル表を全テーマに複製することになり、`container` のスタイル（`dim`・`dashedGroupStroke`・パレット）に二重の保守が生じる。props で十分。
  - ノードを平たい楕円にする `flatten`（#577 の本文にある選択肢）: 研究で、ラベルを上に出すと対応線と文字がぶつかり読みにくいと決めたので採らない（円は直立のまま）。必要なら `props.flatten` として後から足せる。
  - 平面座標のまま全体を配線してからノードも写す: 直交の脚と交差判定は平面座標で閉じるが、平面をまたぐ辺と外の辺はページ上でないと配線できない。平面ごとに小さなレイアウトで配線して写す方が、ルーターの変更なしで済む。
  - 対応線のゴーストを PPTX にも入れる: 要素の複製が PPTX の要素対応（名前・接続点）を乱す。
- **既知の制限と今後**:
  - **平面上の `matrix`（attention map などの重ね合わせ）は未実装**。`matrix` は入れ子のグループ（フレーム + セル）に展開されるが、平面は「ノードだけ」を持つ前提（入れ子のグループは各自の写した枠・ラベル位置・内側の配線が要る）。issue #577 の本文にあるので、#577 は閉じず別 issue で扱う。
  - 平面は自然な大きさ（`stretch`・`justify` で伸ばさない）。
  - 平面内の `route: curve`、平面をまたぐ辺で `route` のないもの（ページ上で直交配線）は写さない。`checkRoutes`（テスト用の検査）は平面内の写した直交経路の「直交」「ポートに垂直」を検査できないので、テストでは平面座標へ戻して直交を確かめる。
  - 3 枚以上の平面で、対応線が真ん中の平面を貫く場合、隠すのは 2 端のうち上の平面だけ（真ん中の平面の上には線が出る）。
  - 平面の `caption`（中心寄せの別ラベル）はタイトルと重なりうるので、平面のタイトルは `label` を使う。
- **互換性**: 既存の図・作例・再現図・ギャラリーの出力は変わらない（`gallery:check` で SVG の差分なし。変わったのは `container` の props の表だけ）。追加は、`sumi/container` の catalog の表、ベースレイアウト `stacked-planes` の SVG・PNG、`previews.json` の 1 行。
